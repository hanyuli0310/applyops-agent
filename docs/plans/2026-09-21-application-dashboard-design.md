# ApplyOps 投递实时仪表盘设计

日期：2026-09-21  
范围：ApplyOps v0.2 前端仪表盘

## 目标

把现有的四个功能页面升级为“总览优先”的投递控制台。用户进入应用后，第一眼看到所有岗位的实时状态、当前最需要处理的事项和下一步操作；资料、岗位偏好和历史记录继续保留为侧边入口。

## 页面结构

默认页面为“投递总览”，而不是资料页。顶部显示四个可点击的统计卡片：待处理岗位、正在投递、等待用户回答/审批、已完成或需要核实。中部突出当前最需要注意的岗位；下方显示全部岗位队列，支持按状态、公司和平台筛选。右侧或底部固定显示待处理事项。

单个岗位卡片展示职位名称、公司、地点、当前阶段、进度、最近活动时间和下一步按钮。点击岗位后在右侧打开详情抽屉，不离开总览页面。

视觉语义统一为：蓝色表示进行中，黄色表示需要用户处理，绿色表示已确认完成，红色表示失败或风险。页面保留手动刷新和最后同步时间。

## 数据流

不新增前端独立状态机，直接复用后端数据：

- `/api/status`：整体运行、资料和简历状态
- `/api/applications`：岗位队列
- `/api/requests`：回答、审批和人工处理事项
- `/api/runner/status`：后台运行和自动策略
- `/api/applications/{id}`：岗位详情、尝试和事件时间线

状态展示映射：

| 后端状态 | 页面文案 |
| --- | --- |
| `queued` | 排队中 |
| `preparing` | 准备申请 |
| `waiting_for_input` | 等待补充信息 |
| `waiting_for_approval` | 等待提交审批 |
| `submitting` | 正在提交 |
| `submitted_verified` | 已确认提交 |
| `submitted_unverified` | 需要核实 |
| `failed` | 投递失败 |
| `cancelled` / `skipped` | 已跳过 |

岗位详情包含事件时间线：入队、路线识别、字段读取、字段填写、简历验证、审批摘要、审批、提交和结果核实。

## 组件

- `DashboardPage`：总览和刷新协调
- `MetricCards`：核心统计
- `ActiveApplication`：当前重点岗位
- `ApplicationQueue`：岗位列表和筛选
- `ApplicationDetailDrawer`：详情、事件、字段和操作
- `AttentionPanel`：待回答、待审批、待核实事项
- `RunnerStatus`：运行、暂停和自动策略
- `StatusBadge` / `ProgressBar`：统一状态展示

现有资料、岗位偏好和历史页面继续保留。详情抽屉复用已有操作：重新准备、回答问题、批准、拒绝、提交、核实和取消。

## 错误和风险展示

网络错误时保留上一次数据，明确显示连接中断、最后同步时间和重试按钮。后端拒绝显示具体原因，例如额度不足、浏览器占用或审批过期。`submitted_unverified` 只允许重新读取页面或人工核实，不显示自动重试提交按钮。

## 验证

实现后需要通过 TypeScript/Vite build、现有 Python 测试、状态映射测试，以及本地 Demo ATS 的完整投递流程。还要检查断网、等待审批、失败和未核实状态，以及桌面和窄屏布局。
